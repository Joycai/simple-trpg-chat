# 单会话登录 规格审查

> 审查对象：[`SSO_SPEC.md`](../spec/SSO_SPEC.md)
> 审查分支：`review/sso-spec`
> 对照实现：`src/auth.ts`、`src/auth.config.ts`、`src/lib/login-history.ts`、`src/lib/rate-limit.ts`、`src/lib/events.ts`

> **业主决策已并入**（2026-06-19）：
> ① 术语更正为「单会话登录 / Single Session」（非 SSO）；
> ② **取消「继续/取消」确认弹窗** —— 采用最小开销方案：新登录直接顶号成功，旧令牌失效；
> ③ 被顶用户**非实时**告知，下次交互时回登录页并展示「已在别处登录 + 来源 IP」；
> ④ 限流封禁暂缓不实现；⑤ Bot 豁免、管理员不豁免。
> 规格已据此重写。

## 1. 结论速览

最终方案是**「无提示的后登录者优先（last-write-wins）+ 失效告知」**，这恰好**复用代码库中已有的会话令牌轮换机制**，是所有备选里开销最小的一种。规格目标基本已被现有实现覆盖，**真正需要新增的只有「会话失效时不再静默登出，而是带原因回登录页展示」这一处**。

| 规格要求 | 现状 | 评级 |
| --- | --- | --- |
| ① 同账号同一时刻仅一个会话（后登录者优先，无提示） | **已实现**（`users.session_token` 轮换） | ✅ |
| ② 旧会话被新登录失效 | **已实现**（令牌不一致即失效） | ✅ |
| ③ 被顶用户下次交互回登录页 + 展示「已在别处登录」+ 来源 IP | 未实现（当前静默登出，未展示原因/IP） | ❌ |
| ④ 失效原因区分「被顶号」vs「被封禁」，文案不同 | 未实现（`isSessionValid` 把两者合并为一个布尔） | ❌ |
| ⑤ 顶号限流封禁 | **业主决策：暂缓不实现** | ⏸️ |
| ⑥ Bot 豁免、管理员不豁免 | 天然满足（见 §3.4） | ✅ |

## 2. 设计取舍与残留风险

### 2.1 术语（已更正）
原标题「单点登录 / SSO」为笔误。**SSO（Single Sign-On）** 指跨系统统一认证，与本规格无关；规格描述的是**单会话登录 / 登录互斥（Single Session）**。规格已全文更正并加术语说明。

### 2.2 取消确认弹窗的代价：ping-pong 顶号
因砍掉登录前的「账号已登录，继续/取消」提示，User2 登录时**不会被告知该账号已有人在用**，直接顶号成功。若两人共用同一账号，会**互相顶号、来回踢出**。对本工具场景可接受，规格已写明此取舍。

> 副带好处：无需「活跃会话检测」「会话过期列」「登出清理令牌」等任何额外机制——因为没有任何流程再去读 `session_token` 判断「是否在线」，登出后 cookie/JWT 自然失效，DB 残留令牌无害。这正是「最小开销」的来源。

### 2.3 IP 来源的可信度（需知悉）
展示给被顶用户的 IP 取自 `login_history` 最近一条记录，源头是 `x-forwarded-for`（`src/lib/login-history.ts:21`、`src/auth.ts:36`）。该值**仅在受控反向代理后可信**；直连或伪造场景下 IP 可能错误或被伪造。作为「仅供参考的提示信息」可接受，但不应据此做安全判定。

### 2.4 IP 隐私（属预期）
向被顶用户展示顶号者的 IP 属轻微隐私暴露，但这正是规格要的「告知在何处登录」，为预期行为。

## 3. 实现差距详述

### 3.1 已具备（①②，无需改动）
- `src/auth.ts:69-80`：每次成功登录生成新 `sessionToken` 写入 DB，旧 JWT 随即对不上。
- `src/auth.config.ts:75-92`：`session` 回调校验 JWT 内 `sessionToken` 与 DB 是否一致，不一致标记 `invalidated`。
- `src/auth.config.ts:4-30`：带 30s TTL 的内存缓存 `isSessionValid`，DB 出错时 fail-closed。
- `src/lib/login-history.ts:33-62`：每次登录记录 IP / UA / 设备类型，保留最近 30 条 —— **来源 IP 已现成**。

### 3.2 需新增：失效时带原因回登录页展示（③）
当前 `src/auth.config.ts:82-88` 检测到失效仅置 `invalidated` 标志，随后在 `src/auth.ts:101-104` 静默返回 null（被动登出），**不展示任何原因**。需改为：

1. 判定为「令牌不一致」失效时，读取该用户 `login_history` **最近一条**的 IP；
2. 重定向回登录页并展示「您的账号已在 IP:xxxx 登录，本会话失效」。

> 「下次交互」最长有 30s 延迟（缓存 TTL，`src/auth.config.ts:5`），符合「非实时」预期，无需改动。
> 实现可走 URL query（如 `/login?reason=elsewhere&ip=xxx`）或一次性读取，避免重复提示。

### 3.3 需调整：拆分失效原因（④）
`isSessionValid` 现在返回 `dbToken === tokenSession && !isBanned`，**把「令牌不一致」与「被封禁」合并成一个布尔**（`src/auth.config.ts:26`）。需拆开返回具体原因：

- **令牌不一致** → 本规格的「已在别处登录」文案。
- **被封禁** → 走原有封禁提示（`banned`），不归本规格。

### 3.4 Bot 豁免 / 管理员不豁免（⑥，天然满足）
- `src/auth.ts:48`：Bot 账号（`user.isBot`）直接被拒登录，天然不参与令牌轮换 —— **Bot 豁免已满足**。
- 管理员与普通用户共用同一 `authorize` 路径，令牌轮换同样生效 —— **管理员不豁免已满足**。
- 实现 §3.2 / §3.3 时**不要**对管理员加任何豁免分支即可。

### 3.5 限流封禁（⑤，暂缓）
现有 `src/lib/rate-limit.ts` 仅用于密码爆破防护（密码错误才计数），与顶号无关，无需改动。「掌握密码即可锁死账号」的自锁风险是暂缓主因，留待后续单独评估。

> **实现状态（已完成）**：§3.2 / §3.3 已实现 —— `getSessionStatus` 区分 `valid`/`token_mismatch`/`banned`/`unavailable`，
> 顶号时取最近登录 IP；`authorized` 回调将被顶用户重定向至 `/login?reason=elsewhere&ip=...`，登录页展示「已在别处登录」提示。
> §3.4（Bot/管理员）天然满足，§3.5（限流）按决策未动。测试见 `src/lib/__tests__/banned.test.ts`。

## 4. 落地建议

单个小 PR 即可，无需拆分、无新增数据列、无新增基础设施：

1. **拆分失效原因**（§3.3）：让 `isSessionValid` / `invalidated` 携带「被顶号」或「被封禁」。
2. **失效告知**（§3.2）：被顶号失效时读最近登录 IP，重定向回登录页并展示文案；`LoginForm.tsx` 增加对应错误/提示分支与 i18n 文案（`messages/{zh,en}.json`）。
3. **测试**：扩展 `src/lib/__tests__/banned.test.ts`，覆盖「令牌不一致 → 已在别处登录文案」「被封禁 → 封禁文案」「Bot 不受影响」「管理员同样被顶」。
4. ⏸️ 限流封禁（⑤）不在本轮范围。

## 5. 业主确认记录

- ✅ 术语：单会话登录（Single Session），非 SSO。
- ✅ 取消确认弹窗，采用无提示的后登录者优先（last-write-wins），接受 ping-pong 取舍。
- ✅ 失效告知非实时，下次交互回登录页 + 展示「已在别处登录」+ 最近登录 IP。
- ✅ 限流封禁暂缓不实现。
- ✅ Bot 豁免、管理员不豁免。
